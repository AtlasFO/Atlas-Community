## Final Report Contract (client-facing)

The report is read by a human IR analyst, not by Atlas's tooling. Each rule below answers a complaint readers of forensic reports commonly raise about the *writing*. `write_final_report` / `write_projected_final_report` lint for R1 and the recommendation-scope rule (advisory, one revision cycle, never a deadlock).

**Investigation-driven reporting (required).** The report is a **projection** of **Current Investigation State** (Claim Graph + investigation memory + journal continuity under `.atlas/`). It is never the source of truth.

1. `misc.current_investigation_state` (full snapshot; `claim.snapshot` is the claim-graph subset)
2. Attach evidence references on claims (`record_ref` / `call_id` / `artifact+locator`) so Supporting Evidence and the Attack Timeline can be resolved
3. `misc.write_projected_final_report` — **required** final write path (TOC, Key Findings, Detailed Findings with RAW EVENT evidence, curated Attack Timeline)
4. `misc.write_final_report` with freeform markdown is **refused** when beliefs exist (cannot bypass the Evidence Resolver)
5. **Custom analyst extracts** (host/site splits, briefings, notes from chat) are **not** the official final report: use `misc.write_case_document(output_path=..., content=...)` under `analysis/` or `reports/`. Never use `misc.batch_run` / python / shell to write report files.

Prefer a curated Attack Timeline built from deterministically resolved evidence events. If timeline readiness fails **but findings (or a partial CIS) exist**, `write_projected_final_report` still writes a **degraded** report with an explicit "Timeline unavailable" section and Limitations — do not invent timeline rows in prose, and do not loop Collect forever waiting for a perfect timeline.

- **R1 — Tool noise.** An internal tool failure or workaround appears in the report **only** when it caps a conclusion's tier or leaves a case question open — and then in the evidence-gaps section, naming the affected conclusion ("PECmd unavailable → TOOLX.EXE original path unrecoverable → binary ID stays LIKELY"). A failure you fully worked around (parser errored → queried the SQLite directly) changed nothing for the reader; it stays in the trace. Title the section "Evidence Gaps Affecting Conclusions", not "Tool Limitations".
- **R2 — Negative results.** Phrase every negative observation as the conclusion it supports: "Recycle Bin empty (0 entries) → recovery via Recycle Bin ruled out". A bare "the Recycle Bin is empty" makes the reader ask *why is this here*. If it supports no conclusion, omit it.
- **R3 — Alternative scenarios.** A competing benign/red-team/simulation explanation gets at most **one** caveat sentence, only where an on-host artifact supports it, and only in the finding it affects — never repeated in the executive summary. Tier honesty (SUSPECTED + what evidence is missing) already communicates the uncertainty.
- **R4 — Number provenance.** Every count, size, or duration carries its derivation inline: "1,000 files (MFTECmd `$MFT` parse: records with extension `.locked`)". A bare number reads as a guess even when it was counted.
- **R5 — Intel vs. evidence.** When intake threat intel shaped a conclusion ("actor profile says phishing initial access"), say so explicitly and separately from what the host evidence shows. The reader must be able to tell expectation from observation.
- **R6 — No emoji.** Never put emoji or pictographic characters in a report, a finding, a note, a case document or any text that reaches the trace. Use plain words: "verified", not a check mark; "warning", not a warning sign. The output is a professional forensic deliverable, and pictographs render inconsistently across the platforms and fonts a reader may open it in.

**Recommendations are recorded, not written.** Section 7 is a projection of the recommendation nodes the run recorded with `claim.record_recommendation` — record them as findings land, each resting on named claim/conclusion ids, with `phase`, `scope` (`host` | `network` | `estate`) and `urgency`. Scope must match what the findings establish: when CONFIRMED/LIKELY findings show an impact TTP (T1486/T1490), multi-host exposure, or high-privilege attacker activity (log clearing, PsExec, DC access), host-local sweeps are **not enough** — record the estate-level decisions the IR team faces (containment/isolation, domain-wide credential hygiene including krbtgt when a DC is in reach, backup integrity verification before restore, data-leak impact assessment when double extortion is claimed, IR/management escalation) with `scope=estate`, citing beliefs on more than one host. Precautions seeded from *What you already know* appear with the source `prior_knowledge` and no basis; the report labels them as such. `reason.pre_report_check` says so when substantiated findings have no recommendation resting on them. On an examination (a device or image examined after the fact), the first recommendations are the investigative follow-ups the findings open: whom to identify, which provider or operator to ask for records, what to preserve, each recorded with phase `investigate` or `escalate` on the finding it rests on. Hardening is a lesson for the owner and comes last; the pre-report check says so when findings name accounts or addresses a third party holds records of and no follow-up rests on any finding.

**Multi-host cases (>1 system in the evidence table).** Tag every finding with `host=` (the evidence-table hostname) — the per-host disposition table, `correlate.killchain_timeline`'s `per_host` buckets, and per-host reports all group on it. Investigate hosts via the normal DAIR host-pivot flow. At Report, after one passing `reason.pre_report_check`, write one per-host report then the estate report — the **estate report is the primary client deliverable** and must contain: the per-host disposition table (Host | Status | Basis), the cross-host timeline (who moved where, when, with what privileges), estate-level synthesis, and estate-scoped recommendations.

**Preferred filenames (snapshot-friendly):** `reports/estate_report.md` and `reports/host_<HOST>_report.md` (legacy `reports/<CASE>_estate_report.md` / `reports/<CASE>_<HOST>_report.md` still accepted by lint and scope inference).

**Executive Summary is for management:** a brief, plain-language account of what happened, what was affected and what is still uncertain — no event ids, tool names, paths, hashes or identifiers; the technical depth lives in Detailed Findings.

**Standard report spine (all complete reports):** Table of Contents → Executive Summary → Answers to the Investigation Questions (derived from the conclusions linked to each task — see 03, "Closing a question") → Scope and Evidence → Key Findings → Detailed Findings (authoritative; once per stable `F-NNN`) → Attack Timeline → Evidence Gaps → Recommendations → Appendix.

**When a finding exists.** One finding per distinct conclusion about an artifact or event: what happened, where, when, and what shows it. Repeated sightings of the same thing (every packet of one session, every row naming one file, every hit of one pattern) are supporting evidence of that one finding, not new findings — put them in `supporting_evidence` and cite the calls that produced them. Before recording, ask which recorded finding this observation belongs to; if one exists, the observation extends it — attach the new evidence with `claim.add_observation` linked to that finding's claim, or record the sharper statement and `claim.supersede` the older claim — it does not start a new one. `record_finding` folds a restatement of a recorded finding (`duplicate: true`, `near_duplicate_of`) and marks a sharper one as its refinement (`refines_call_id`). A run whose findings far outnumber the case's questions is told so (`volume_advisory` on `record_finding`); the answer is to fold observations into findings and to close questions with `claim.promote_conclusion` + `misc.update_investigation_task`, not to record more.

**Detailed Findings shape.** Each finding renders as a short title (what, where, when), then *What happened* (your Summary), *Why it matters* (your Assessment), and at most three validated citations in the form `Host · Artifact · Record · Time — value`. Write the `### F-NNN — short title` line as a plain-language headline, not a restatement of the claim. Supporting Evidence is injected by the provenance-first Evidence Resolver (`record_ref` → `call_id` → artifact+locator; correlated matches are labeled; never silent nearby guesses). Language: `atlas run|rerun -L en|de` persists in `.atlas/case_config.json`.
